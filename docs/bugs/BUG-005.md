# BUG-005：公共 Agent 用无关 Repository Evidence 回答未知项目

状态：`verified/closed`

关联 Plan：[PLAN-024](../plans/PLAN-024.md)

## 现象与影响

“牛鼻子”公开 Agent 当前只授权了 OneCat Repository。用户先询问 OneCat 后再问 `askme 项目呢？`，旧实现仍基于 OneCat Evidence 生成一段 OneCat 项目介绍，而不是明确说明没有 Askme 的授权证据。回答中的 OneCat 事实虽然真实，但与问题核心实体不一致，破坏了“每个回答只由当前问题相关授权 Evidence 支撑”的边界。

## 根因与促成因素

- 旧 Retrieval Trace 已记录 `entities=["askme"]`、`unsupportedAspects=["askme"]`，但 Evidence Judge 把 OneCat 文档中的通用词“项目”当成覆盖信号，因此先后可能得到 `partial` 或因无关正反句得到 `conflicted`；两种结果都会继续进入 Answer Generator。
- 第一次收紧 Coverage 后，Askme 已正确得到 `none`，但 Public Chat 和 Candidate Preview 在 RAG 证据不足时仍会把“唯一可用 Repository”无条件当成 Deep Analysis 目标。该 fallback 绕过了 Router 的 `refuse / repositoryId=null` 结果，再次把 Askme 问题绑定到 OneCat。
- 初版 fallback 修复只要求 Router 返回一个授权 Repository。Change Review 进一步确认这仍不足以构成 Host 不变量：Router 是模型决策，偶发把 Askme 映射到 OneCat 时仍可能越界。

## 修复

- Evidence Judge 优先检查 Planner 提取的实体；核心实体在选中 Evidence 中没有字面支持，且 Rerank 降级或最高相关性不足时，先于冲突判定收敛为 `none`。
- 高置信语义 Rerank、相关问题和多轮已解析实体仍保留 `partial/full` 资格，不把门禁扩大成全文精确匹配。
- RAG 证据不足后的 Deep fallback 不再猜测唯一 Repository。Public Chat 与 Candidate Preview 只在 Router 选择了当前授权且允许 Deep 的 Repository，并且问题文本明确点名该 Repository 时才允许进入 Deep。

## 验证与预防

- 回归测试覆盖 Askme + OneCat 无关 Evidence、无关正反 Evidence、强语义但无字面实体、相关多轮指代，以及 Router 误选唯一 OneCat 与显式点名 OneCat 两种 fallback。
- 最终自动化为 `101 files / 364 tests`，ESLint、Typecheck、production Build `31 / 31`、Surface Matrix 与 `git diff --check` 全部通过。
- 最终本地真实 API 和浏览器都证明：直接问 Askme、OneCat 后追问 Askme 均返回 `INSUFFICIENT_EVIDENCE`、0 Citation；OneCat 问题仍返回正常回答和 6 个公开引用。
- 最小预防措施是把“核心实体覆盖”和“Deep Repository 唯一确定”保留为 Host 端确定性门禁；Router、Rerank 与 Generator 的模型判断只能在该门禁内提供信号，不能单独扩大回答或源码分析范围。
