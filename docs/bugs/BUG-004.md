# BUG-004：delivery trace 因 Journal 正文提及历史 Plan 而误匹配

状态：`verified/local-fixed`

关联 Plan：[PLAN-008](../plans/PLAN-008.md)

## 现象与影响

`PLAN-008` 的 delivery Journal 在 Evidence 中提及 `PLAN-001` 历史 audit 后，对 `PLAN-001` 重跑 audit 只报告“缺少决策矩阵”，不再报告“缺少 delivery Journal”。但当前 Journal 的 `Plan` 字段明确指向 `PLAN-008`，它不应被当作 `PLAN-001` 的交付记录。

该误判会使历史 audit 丢失真实缺口；如果其他活动 Plan 的 Journal 正文提及当前 Plan ID，也可能让 strict close 误用不属于该 Plan 的 Journal。

## 根因与触发条件

`validate_delivery_trace.py` 的 `delivery_journals` 通过 `current_plan_id in text` 搜索整份 Journal。这只能证明正文出现过 Plan ID，不能证明 Journal 的归属关系。

稳定触发条件是：

1. Journal 的 `记录类型` 为 `delivery`；
2. `Plan` 字段指向 Plan B；
3. 其他正文提及 Plan A；
4. validator 对 Plan A 查找 delivery Journal。

## 修复

- `delivery_journals` 只从 Journal 的 `Plan：` 字段解析 Plan ID，并与当前 Plan ID 精确比较。
- 新增回归测试：`PLAN-008` Journal 正文提及 `PLAN-001` 时，只能匹配 `PLAN-008`。
- 更新 Askme 安装 manifest 中 validator 的 SHA-256，使当前托管文件状态可对账。

## 验证与预防

- Red：修复前回归用例将 `PLAN-008` Journal 错误返回给 `PLAN-001`，产生 1 个断言失败。
- Green：修复后回归用例通过。
- `PLAN-001` audit 恢复为 `0 errors, 2 warnings`，同时报告决策矩阵和 delivery Journal 历史缺口。
- `PLAN-008` strict delivery trace 保持 `0 errors, 0 warnings`。
- 预防原则是只从拥有关系的结构字段解析身份，不用整文子串出现代替 owner 契约。

AutoGo 源实现尚需同步该回归与修复；本次只在 Askme 当前授权范围内完成本地修复，不跨项目创建 Commit。
