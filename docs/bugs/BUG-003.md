# BUG-003：Docker 重启时 worker 可能原样输出 PostgreSQL 客户端对象

状态：`verified/closed`

关联 Plan：[PLAN-006](../plans/PLAN-006.md)

## 现象与影响

隔离 Docker 生命周期验收同时 restart db、web 与 worker 时，worker 的容器日志出现由 Node 事件系统展开的 PostgreSQL client/pool 对象，而不是项目约定的结构化错误事件。观测到的对象包含连接内部状态；即使本次截取中没有证明真实 Secret 已输出，继续依赖默认展开会让日志字段失控，并增加连接配置泄露风险。

## 根因与触发条件

worker 为 heartbeat 和 ingestion 共用 `pg.Pool`，但没有监听 pool 的后台 `error` 事件。db 在 idle client 存在时重启会触发该事件；Node 对未处理事件采用原生错误输出，绕过了项目的 `toAppError` 和 JSON 字段白名单。同步 restart 是稳定触发条件，业务请求本身不是根因。

## 修复

- 为 worker pool 注册 `error` listener，把事件转换为只含 `event=worker.pool.error`、`workerId` 与稳定 `errorCode` 的 JSON 日志。
- 保留 heartbeat、job loop 与顶层失败各自的结构化错误边界，不记录 Error message、stack、client、连接串或请求/资料正文。
- Docker 生命周期验收在 restart 后重新解析随机宿主端口，并扫描数据库、SMTP、Candidate/Admin、DeepSeek Secret 与私有资料正文哨兵。

## 验证与预防

- 隔离空库栈完成真实资料上传、worker 索引后同步 restart db/web/worker；同一 session、material、knowledge、job、request audit 和 file checksum 全部恢复。
- restart 日志包含 `worker.material.indexed` 与 `jobId`，所有 Secret/私有正文哨兵均未出现；临时容器、network 与两个 volume 已精确清理。
- `src/server/http.test.ts` 证明 5xx API 日志只含 request ID、error code、status 和 cause type，私有 Error message 不进入日志。
- 最小预防措施是在具有后台连接池的进程上显式处理 pool error，并把重启故障与 Secret sentinel 扫描保留在隔离生命周期验收中。
