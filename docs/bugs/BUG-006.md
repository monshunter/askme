# BUG-006：RAG 运行时评测被 SQL 枚举与跨 owner fixture 假设破坏

状态：`verified/closed`

关联 Plan：[PLAN-026](../plans/PLAN-026.md)

关联 Operation：[OP-010](../operations/OP-010.md)

## 现象与影响

Query-understood RAG V4 在单元测试、Typecheck、Lint 与 production Build 通过后，首次进入真实 PostgreSQL/Provider 评测时，17 条实际检索用例统一失败为 `operator does not exist: rag_source_kind = text`。修复 SQL 后，使用单一 `ASKME_RAG_EVAL_OWNER_ID` 的评测又出现互斥结果：Askme/Repository 用例只在默认 Candidate 通过，富途/履历用例只在公开简历 Candidate 通过，换 owner 会让另一组全部失败。

前一个问题如果直接发布，会让进入检索的 Candidate/Public 问答在 PostgreSQL 层失败；后一个问题不会影响产品运行，但会让验收把授权数据不存在误报成 Query Understanding 回归，也可能促使实现为通过错误 fixture 而放宽 Evidence 门禁或跨 owner 复制资料。

## 根因与促成因素

- 四路检索共用 eligible CTE 新增 source kind 过滤时写成 `source.source_kind=ANY($5::text[])`。`source_kind` 是 PostgreSQL enum，不能与 `text[]` 直接比较；Pool mock 只验证 SQL 片段和参数位置，不执行真实数据库类型检查。
- 旧运行时 fixture 只覆盖默认 Candidate 的 Askme/Repository 数据，只有一个 owner 环境变量。新增无实体时间、项目、技能与富途用例后，脚本仍假设这些真实材料属于同一 owner；实际上简历材料位于另一个 Candidate，授权隔离正确阻止了交叉检索。
- 首轮评测只选“最早 Candidate”，没有先把 fixture 的知识前置条件与 owner 数据对账，导致 SQL 根因修复后的质量失败最初看起来像 Planner/Answerability 假阴性。

## 修复

- 将共用过滤改为 `source.source_kind=ANY($5::rag_source_kind[])`，保留四路完全相同的 owner、visibility、active source、entity scope 与 source-kind 排名前过滤。
- 更新定向测试，固定 enum array cast 与 `$5` 参数位置；继续由真实 PostgreSQL runtime eval 覆盖 mock 无法证明的 SQL 类型行为。
- Runtime case 增加显式 `dataset=entity|profile`。`ASKME_RAG_EVAL_OWNER_ID` 只拥有 Askme/Repository 用例，`ASKME_RAG_PROFILE_EVAL_OWNER_ID` 只拥有真实简历用例；每个 case 的检索、scope 检查和 Citation Validator 都使用对应 owner。
- API eval 同样拆分数据事实：默认 Candidate/Public 验证 Askme、Repository、无实体项目与 fail-closed；独立简历 Public 会话验证原始 2022–2024 时间问题、incidental Askme 与富途 focused 问题，不伪造一个同时拥有两套资料的账户。

## 验证与预防

- SQL 修复后的双 owner 真实 PostgreSQL/Provider 评测为 `26 / 26 PASS`，包含 24 条行为用例与 2 条 Provider 降级用例；HTTP 评测为 `16 / 16 PASS`。
- Query Semantics `20 / 20 PASS`，required role 假阳性、required entity 漏识别、discovery false-none 与 entity substitution 均为 `0`；核心评测 `120 + 12 + 10` 条无失败。
- Vitest `105 files / 423 tests`、ESLint、Typecheck、production Build `31 / 31`、Surface Matrix 和 `git diff --check` 全部通过。
- 最小预防措施是：涉及 PostgreSQL enum/cast、CTE 参数或真实 owner 授权投影的检索变更，单元 SQL shape 测试不能替代 Compose 网络内的真实数据库评测；运行时 fixture 必须显式声明知识数据集 owner，不允许根据“Candidate”角色推断所有验收材料属于同一 tenant。
