# BUG-001：真实文件上传因数据库 schema owner 漂移返回 207

状态：`verified/closed`

关联 Plan：[PLAN-003](../plans/PLAN-003.md)

## 现象与影响

Computer Use 从 macOS 原生文件选择器上传合法的 844-byte Markdown 时，页面显示 0 个文件入队、1 个失败；实际 `POST /api/materials/upload` 返回 207、`INTERNAL_ERROR`。自动化文件校验和直接数据库 INSERT 均正常，因此问题只出现在应用的 Drizzle 写入/返回链路。

## 根因与促成因素

migration `0010_answer_source_invalidation.sql` 把 `source_invalidated_at` 添加到 `messages`，但 `src/server/db/schema.ts` 把同名字段声明在 `materials`。Drizzle 按错误 schema 生成包含不存在 materials 列的 SQL，服务端再把数据库异常安全投影为通用 5xx。此前测试分别验证 migration 行为和上传校验，没有验证迁移后的表字段 owner；通用批量失败文案也隐藏了具体失败文件与服务端原因。

## 修复

- 将 `sourceInvalidatedAt` 从 `materials` 移到 `messages`。
- 新增 schema ownership 测试，直接保护两个表的字段边界。
- 上传反馈显示失败文件及服务端安全错误，同一文件选择前清空 input，使失败后可以原样重试。

## 验证与预防

- Red 测试在错误 schema 上准确失败；修复后 schema、反馈与文件校验共 3 files / 15 tests PASS。
- 同一原生文件重试返回 201，随后由 worker 收敛到 Indexed；数据库存在 material、chunk、job、Knowledge Item 和 Evidence 完整关系。
- 全量验证为 31 files / 108 tests PASS，生产 Docker upload smoke 与 ready PASS。
- 最小预防措施是继续让 schema ownership 测试随新增 migration 同步扩展，不再只依赖 migration 执行成功证明 ORM schema 一致。
