# EVO-001：Askme 全量交付 Harness 流程复盘与渐进式闭环提案

状态：`proposed`（等待 Human Gate，尚未应用）

类型：`Proposal`

审计范围：`OBJ-001`、`PLAN-001` 至 `PLAN-006`、`SPEC-001`、`DESIGN-001` 至 `DESIGN-004`、`REVIEW-001` 至 `REVIEW-026`、`OP-001` 至 `OP-005`、六个功能交付 Commit 与一个状态修正 Commit。

## 1. 结论

用户指出的四个现象均有当前仓库证据，但根因并不完全相同：

1. **Spec 没有按能力逐层展开，属于 Harness 模型与门禁缺口。** `SPEC-001` 自称唯一父 Plan 为 `PLAN-001`，后续五个 Plan 却都把它作为自己的关联 Spec。四份 Design 证明项目并非完全缺少技术设计，真正缺失的是“Objective 验收合同 → Plan-owned capability Spec → 对应 Design”的渐进式契约链。
2. **Journal 缺失主要是关闭顺序与 owner 设计缺口。** 当前没有独立 Journal Skill；`autogo-change-close` 在第 5 步先创建 Commit，第 7 步到整个 Objective 完成后才“判断是否需要 Journal”，因此无法保证提交前保存本次交付上下文。
3. **Session Review 缺失既是 Agent 执行遗漏，也是关闭门禁缺口。** 本次交付有 26 份 Review，其中 4 次 `FAIL`、1 次 `BLOCKED`，明显满足复杂工作结束、重复失败和用户介入触发条件，却没有任何 Session Review 或 Evolution 记录；同时现有关闭流程没有校验这一结果。
4. **Scenario 缺失是明确的 Skill 执行遗漏，且 Change Review/Close 未能拦截。** `autogo-e2e-run` 已要求测试结束后更新 Scenario 与 Index，但仓库已有 15 个浏览器 fixture、smoke 或生命周期脚本和 5 份 Operation 运行记录，`docs/scenarios/` 仍只有 README/空 Index。

共同系统原因是：Harness 已定义多数局部能力和文档 owner，但 Spec 分解、Scenario、Session Review、Journal 仍是可跳过的旁路，没有进入 Standard Commit 的可验证关闭不变量。结果是实现和运行 Evidence 可以成立，知识传递与下一次复用却无法随 Commit 一起闭环。

## 3. 发现与根因

### F1：Plan 拆分没有带动契约拆分

当前 Plan 已按资料、隐私/Agent、Admin、UI 和运行验收拆成六段，但 Spec 始终只有一个。后续每个功能 Commit 继续修改 `SPEC-001` 的 AC 勾选，而没有创建属于当前 Plan 的能力合同。

这不是简单的“Agent 少建文件”：

- 根 Standard graph 只要求按 Skill description **按需**调用 Spec，没有契约分解检查点；
- `autogo-spec-write` 要求 Spec 链接唯一父 Plan，现有结果却没有被 Plan Review 或 Change Review 判为冲突；
- 顶层 Spec 同时保存产品全貌、详细行为和跨六个 Plan 的完成状态，导致后续 Agent 必须加载整份合同才能理解一个局部能力；
- 技术细节主要集中在全栈 `DESIGN-001` 和三个后期专项 Design 中，无法稳定地从某个 Plan/AC 定位到接口、状态、失败和恢复设计。

因此，正确改进不是把低层实现塞进更多 Spec。Spec 继续拥有外部行为、边界和 AC；Design 拥有组件、接口、状态、失败恢复和迁移。需要新增的是稳定的层级和一对一 owner 关系。

### F2：Journal 不是 Commit 前置制品

`autogo-change-close` 的输出虽然列出 Journal，但实际步骤为：

1. 第 5 步先创建原子 Commit；
2. 第 7 步只有整个 Objective 全部完成后才判断是否需要 Journal 或 Session Review；
3. 取消时明确要求 Journal，正常 Plan 完成却没有同等确定性规则。

这使“提交自动触发 Journal”在当前模型中做不到。Git 本身也不能调用 Codex Skill；真正可落地的双层机制应是 Agent 在 `git commit` 前自动路由 Journal Skill，并由确定性检查拒绝缺少 Journal 的 Standard close。

当前详细事实散落在 Plan、Review、Operation、Spec AC 和 Git Diff 中。它们各自合法，但没有一份短小的提交级恢复入口说明本次范围、关键决策、验证结果、剩余风险和恢复方式。

### F3：Session Review 触发条件存在，但没有关闭门禁

`autogo-session-review` 已把复杂工作结束、重复失败、用户频繁介入和流程浪费定义为触发条件。`OBJ-001` 至少出现以下信号：

- 4 次 Review `FAIL`；
- 1 次 Change Review 因精确移动视口验收进入 `BLOCKED`；
- 同一天连续关闭 6 个跨数据库、worker、AI、浏览器和 Docker 的 Standard Plan；
- 多次 Reconcile 后仍没有 Observation、Candidate 或 `no-evolution` 结论。

Agent 应当调用 Session Review，因此这里有执行遗漏。但仅依赖自然语言触发描述仍会再次遗漏：`autogo-change-close` 把判断放在 Commit 和整个 Objective 完成之后，Plan Review、Change Review、Git 都不要求存在结果。

每次 Standard Commit 都应产生一次轻量 Session Review 结论，但不应强制每次创建 Evolution 文档。没有可复用改进时记录 `NO_EVOLUTION`；只有 Observation/Candidate/Proposal 才写入 `docs/harness/evolution/`。

### F4：E2E 运行结果替代了 Scenario 合同

当前资产分工实际变成：

- `scripts/smoke-*.ts`、浏览器 fixture 和生命周期脚本保存执行机械；
- `OP-001` 至 `OP-005` 保存当次环境、结果与恢复 Evidence；
- Plan 只写“完成真实 Chrome/E2E”；
- 没有文档保存可复用的前置条件、用户步骤、预期 UI/API/DB 状态、清理动作和 AC 映射。

Operation 不能替代 Scenario：前者证明某个 revision 在某个环境运行过，后者定义下次如何重复同一个用户/系统行为。`autogo-e2e-run` 已要求更新 Scenario，但 Change Review 和 Close 没有验证 `SCN-*`，所以执行遗漏仍能通过整个 Objective。

## 4. 目标模型

### 4.1 渐进式契约链

目标关系为：

```text
根 SPEC.md（产品方向与总边界）
  → Objective Acceptance Spec（跨能力 AC 与非目标）
    → Plan-owned Capability Spec（局部行为、异常、权限、兼容 AC）
      → Design（组件、接口、状态、失败恢复、迁移）
        → Plan Phase / 实现 / 测试
          → Scenario（AC 对应的可复用真实 E2E）
            → Operation / Review（当前 revision 的运行与审查 Evidence）
```

以已完成 `OBJ-001` 为例，合理的渐进式投影应是：

- `SPEC-001`：Objective 级 MVP 验收地图；
- `PLAN-002` 拥有 Materials / Knowledge capability Spec；
- `PLAN-003` 拥有 Privacy / Agent / Publication / Public Chat capability Spec；
- `PLAN-004` 拥有 Admin capability Spec；
- `PLAN-005` 拥有 UI / I18N / A11Y capability Spec；
- `PLAN-006` 拥有 Runtime / Observability capability Spec。

这只是历史回放示例，不建议在未授权时重写已完成 Objective。未来新 Plan 应按以下决策表执行。

| 当前 Plan 变化 | Contract decision | 要求 |
|---|---|---|
| 新增用户行为、公共接口、持久数据语义、权限边界、失败/恢复或兼容语义 | `CREATE` | 创建唯一父 Plan 的 capability Spec，并按需创建/更新 Design |
| 行为已由当前 Plan-owned Spec 完整覆盖，仅补实现或修复 | `REUSE` | 链接现有 Spec 与 AC，说明没有新语义 |
| 纯文档分析、Review、局部重构或已有合同内的运行验证 | `NOT_NEEDED` | 在 Plan Review 写明理由，不创建低价值 Spec |

Plan Review 必须记录 `Contract decision: CREATE | REUSE | NOT_NEEDED` 及链接/理由。一个 Spec 只能有一个 owner Plan；其他 Plan 可以引用它作为上层依赖，但不能把它冒充自己的关联 Spec。

### 4.2 可复用 Scenario

任何 Plan Item 明确要求真实浏览器、跨组件 smoke、from-zero/restart 或部署后 E2E 时，在运行前必须链接至少一个稳定 Scenario。Scenario 最小字段为：

- `SCN-*` ID、状态和关联 Spec AC；
- 目标角色与用户结果；
- 环境、fixture 和前置状态；
- 可重复步骤；
- UI、API、数据库/后台状态的预期结果；
- 清理与恢复；
- 自动化命令或脚本入口；
- 最新 Evidence 只做引用，不复制 Operation 日志。

脚本应在文件头或运行输出中声明对应 `SCN-*`。多个脚本可以支撑一个业务 Scenario，一个脚本也可作为多个 Scenario 的公共机械，不要求一文件一场景。

### 4.3 Commit 前 Session Review 与 Journal

Standard Plan 的关闭顺序调整为：

```text
实现与验证
  → Change Review PASS
    → autogo-session-review
      → NO_EVOLUTION 或更新 EVO
        → autogo-work-journal
          → Plan / Progress / Index / Git 对账
            → deterministic close check
              → atomic git commit
```

如果 Session Review 发现产品、测试或恢复缺陷，返回 Reconcile，不得继续 Commit。只有 Harness 候选才进入 Evolution；没有候选时把 `NO_EVOLUTION` 写入本次 Journal。

建议新增职责单一的 `autogo-work-journal`，并把 Journal 的写 owner 从 `autogo-change-close` 中抽离：

- 每个 Standard Plan 的原子 Commit 前追加一条 delivery 记录；
- Waiting / Cancelled 前追加 handoff/cancel 记录；
- Fast 默认不产生详细 Journal，除非升级 Standard、出现恢复上下文或用户明确要求；
- 最小内容为 Objective/Plan、范围与 Diff 摘要、关键决定、实际验证、未验证项/风险、恢复方式、Session Review 结论和预期 Commit subject；
- 不要求在同一 Commit 内回填 Commit hash，避免“先 Commit 才知道 hash、回填又需要第二个 Commit”的循环。Commit 与 Journal 的实际关联由 `git log -- <journal-file>` 保证。

### 4.4 确定性关闭检查

仅靠 Agent 记住调用 Skill 不足以闭环。建议增加一个只读、可测试的 `validate_delivery_trace`，由 `autogo-change-close` 在 `git commit` 前调用，并由 Harness validation 覆盖：

1. 活动 Standard Plan 存在 Plan Review 的 Contract decision；
2. `CREATE/REUSE` 的 Spec 链接与唯一父 Plan 一致；
3. 含真实 E2E/Chrome/smoke/lifecycle 的 Item 存在 `SCN-*` 链接；
4. 准备关闭的 Plan 在本次 Journal 中有 delivery 记录；
5. Journal 中存在 `NO_EVOLUTION` 或 `EVO-*` Session Review 结果；
6. Scenario、Journal、Evolution 的 Index 与正文一致；
7. 历史已完成 Plan 先报告 warning，不因新规则直接改写或阻断旧 Commit；新的活动 Plan 严格失败。

该检查不创建新的全局状态台账，只验证现有 owner 之间的链接和关闭不变量。

## 5. 建议修改面与复杂度变化

本 Proposal 获批后，建议用一个独立 Harness Evolution Objective 分阶段实施：

| 变更 | 目的 | 复杂度变化 |
|---|---|---|
| 根 Standard graph 调整关闭顺序 | Session Review / Journal 进入 Commit 前主干 | 修改 1 个稳定流程，不新增状态机 |
| `autogo-spec-write`、`autogo-plan-review` 增加 Contract decision 与唯一 owner 校验 | 强制渐进式契约分解 | 增加 1 个三态决定，删除含糊的“按需猜测” |
| `autogo-e2e-run`、`autogo-change-review` 增加 Scenario 前置/收口校验 | 让 E2E 可复用且不可静默遗漏 | 复用现有 Scenario workspace，不新增证据台账 |
| `autogo-session-review` 固定输出四态结果 | 每个 Standard Commit 都有复盘结论 | `NO_EVOLUTION / OBSERVATION / CANDIDATE / PROPOSAL` |
| 新增 `autogo-work-journal`，精简 `autogo-change-close` 的 Journal 写职责 | 建立唯一 Journal 写 owner | 新增 1 个小 Skill，同时消除两个 Skill 的模糊写 owner |
| 新增 `validate_delivery_trace` 与 fixtures | 把自然语言要求变成可回归门禁 | 新增 1 个只读脚本及正反例测试 |

净变化是一个轻量 Skill、一个确定性检查和若干现有路由修订；不新增数据库、外部服务、全局 Evidence ledger、第二套 Plan 状态或 Git hook。Git hook 可选但不推荐作为首版，因为它不能调用 Codex Skill，只能拒绝不完整提交，且会影响人工本地工作流。

## 6. 验证方案

应用阶段至少需要以下当前验证：

1. **正反例 fixtures**
   - 新权限/数据语义 Plan 没有 capability Spec：FAIL；
   - Spec 被两个 Plan 声明为 owner：FAIL；
   - Chrome/E2E Item 没有 Scenario：FAIL；
   - Standard close 没有 Journal 或 Session Review 结果：FAIL；
   - docs-only 分析 Plan 使用 `NOT_NEEDED` 且理由成立：PASS；
   - Fast 局部变更没有详细 Journal：PASS。
2. **历史回放**
   - 对 `PLAN-001` 至 `PLAN-006` 运行 audit 模式，应精确报告本报告中的 Spec owner、Journal、Session Review、Scenario 缺口，不修改历史；
   - 对新建模拟 Plan 运行 strict 模式，补齐对应制品后从 FAIL 收敛到 PASS。
3. **Harness 验证**
   - 运行 `autogo-harness-validate`，确认根合同、Skills 自包含、docs owner、索引和完整参考样例一致；
   - 重复运行索引与 validator 不产生 Diff。
4. **关闭回放**
   - 模拟一次 Standard PASS、一次 Session Review 返回 Reconcile、一次 Waiting、一次 Cancelled，确认 Journal 与 Commit 顺序正确且没有双重状态 owner。

## 7. 兼容、发布与回滚

- 先只对新建或活动 Standard Plan 启用 strict；历史已完成 Plan 仅 audit warning，避免伪造历史制品。
- 先实现 Skill/validator fixtures，再修改根 graph，最后用一个新 Standard Plan 完整 dogfood；顺序失败时可在进入新任务前停止。
- 回滚只需还原 Harness graph、Skills 和 validator Commit；Proposal、历史 audit 与 Journal 保留，不影响产品代码、数据库、Docker 数据或已完成 Objective。
- 如果新门禁产生高频低价值文档，优先收紧 `CREATE` 和 Scenario 适用条件或合并字段，不通过绕过 validator 恢复含糊路由。

当前授权已完成分析与 Proposal，但没有授权修改根 `AGENTS.md`、Skills 或 Harness validator。本 Proposal 的应用动作需要用户明确批准：

> 按 `EVO-001` 建立独立 Harness Evolution Objective，修改根 Standard graph 与相关 Skills，新增 `autogo-work-journal` 和确定性 trace validator，并以新活动 Plan strict、历史 Plan audit-only 的方式验证；不回填或改写 `OBJ-001` 历史制品。

在批准前，`EVO-001` 保持 `proposed`，当前仓库运行合同不变。
